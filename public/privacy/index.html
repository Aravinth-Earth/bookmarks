Privacy — collected links

The privacy policy for Bookmarks — collected links, the optional companion extension for the vault at bookmarks.332321.xyz. It covers version 0.2.5 of the extension and nothing else.

What the extension touches

  • The address of a page. When a tab finishes loading a page served over http or https, the extension reads that tab's address. The #fragment is dropped, credentials embedded in the address (user:pass@) are removed, and query parameters whose name says they are a credential — token, code, signature, session, password and a short list beside them — are stripped before anything is written. That denylist is not complete, so a secret in a parameter nobody would guess is still stored, which is one more reason the rows stay on the device.
  • A row per address. The address, the host taken from it, how many times it has been opened in this browser profile, when it was first and last opened, and whether the visit came from a private window. Nothing measures how long a page stayed open, and nothing records which tab was in front.
  • The settings the vault sent. Whether collection is on, how each site is recorded, the exclusions, retention, the row limit, the daily cap, the visit floor and whether private windows count. The extension keeps a copy so it can apply them while no vault tab is open; the original lives in the vault's own sealed document.
  • A daily counter. The date and how many new addresses were kept that day, which is what the daily cap is applied to.

Nothing else is read or kept: no page content, no page title, no form input or keystroke, no referrer, no cookie, no download, no bookmark, no tab or window identifier, no open duration, and nothing from before the extension was installed.

What it is used for

One purpose, with nothing beside it: showing you the addresses this browser has opened, so the ones worth keeping are one press away. The rows are not used for advertising, profiling, analytics, creditworthiness or lending, and they are not sold.

The one permission that needs a reason

Chromium shows tabs at install as "Read your browsing history". That warning is broader than what this extension does with it, and it is also the reason the permission is asked for plainly rather than hidden: there is no narrower permission that lets an extension see a tab's address, so the address a tab has committed to is only readable through tabs.

The extension reads one field of one tab — the address — at the moment that tab reports it has finished loading. It holds no timer, no dwell state and nothing to compare a visit with, and it never asks the browser for history: history is not among the permissions it requests, and there is no call to a history API in its code. A page opened before the install is therefore not here, and neither is a page the browser did not load while the extension was enabled.

What happens to that address: it is normalised as described above, counted, and written on the device. The list is handed to the vault page when the vault asks for it, and only that page may ask — the extension injects its bridge only into the vault's own pages, and refuses a message from any other origin, extension or frame before a handler runs.

Private windows are left out unless two things are true: the extension has been allowed in Incognito at the browser's own extensions page, and Include private windows is on in the vault's Settings.

The other two permissions

Where it is kept

In chrome.storage.local, inside the profile of the browser the extension was installed in — on that device, as plain text, unencrypted. It is not in the vault, not in any backup the vault keeps, and it is never synced: the sealed copy the server holds is the vault's document and contains none of these rows. An address reaches the vault only when you add it from the vault's own list, and from that moment it is part of the sealed document and covered by the vault's policy rather than this one.

The extension makes no network request at all. Its own pages set connect-src 'none', and the repository's npm run check fails on a fetch, XMLHttpRequest, sendBeacon, WebSocket, EventSource, importScripts, sendNativeMessage or connectNative call appearing anywhere in the extension. Nothing here is sold or shared, and nothing is loaded from anywhere: every byte of the extension ships in the package, its pages set script-src 'self', and there is no remote script, no evaluation of a string as code, and no update channel but the browser's own store.

How long it stays, and how to remove it

The vault decides how long a row is kept and how many rows there may be; a tidy every six hours applies both, and a row past either bound is deleted. Settings → Collected links in the vault has Clear collected links, and turning collection off stops new rows without deleting the ones already there. Removing the extension asks the browser to delete what it stored. Disabling it deletes nothing, and a browser profile that is backed up carries its own copy, so removing is a request rather than a shredder. The vault's bookmarks are untouched either way: they are in the sealed document, not in the extension.
